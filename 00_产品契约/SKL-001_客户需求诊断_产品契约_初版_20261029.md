# SKL-001｜客户需求诊断

> 产品契约初版 v0.2｜资产类型：Skill｜状态：产品定义与内部测试准备中
>
> 本文是私有开发草案，不是 WorkBuddy 发行包；其中不使用客户、项目或个人可识别案例。

## 1. 一句话定义

将零散、模糊或互相矛盾的客户表达与资料，转成**来源清楚、可确认、可推进、可交接**的项目需求判断。

它的价值不在于替用户写一份好看的 Brief，而在于区分：客户已经确认了什么、客户还要提供什么、团队应据此形成什么方案命题，以及哪些问题真正会阻断项目。

**不得把内部方案草案、团队解释或 AI 推断，改写成客户原始需求。**

## 2. 面向谁、在何时使用

| 目标用户 | 典型触发时刻 | 希望获得的结果 |
| --- | --- | --- |
| 策划 / 商务人员 | 收到客户微信、邮件、口头需求后 | 不遗漏关键问题，避免过早承诺 |
| 项目负责人 | 准备立项或开内部启动会前 | 统一团队对范围、风险和下一步的理解 |
| 创意 / 设计负责人 | 需求看似很多却没有核心目标时 | 找到应先解决的问题，而非直接做形式 |
| 小团队负责人 | 判断要不要接、如何接、是否补合同边界时 | 形成可解释的接单判断依据 |

首版重点适用展陈、活动、空间体验、快闪与品牌线下项目；也可用于其他客户委托型项目的轻量初诊。

## 3. 产品承诺与边界

### 产品承诺

1. 忠实区分客户已确认内容、客户补充资料、内部方案解读、AI 推断和待验证事项。
2. 在资料不足时，不仅提出高价值问题，也列出项目进入不同阶段所需的基础输入。
3. 将“团队需要完成的创意与设计思考”与“真正的风险或阻断项”分开呈现。
4. 明确指出目标、受众、内容、媒介、资源、周期、决策链或范围之间的冲突。
5. 让输出可被客户沟通、内部评审、策展大纲、方案深化或下一阶段 Skill 直接使用。

### 不做什么

- 不替代法律、工程、安全、消防、财税等专业结论。
- 不在信息不足时给出精确报价、工期承诺或成功保证。
- 不直接生成完整创意方案、施工方案或项目排期。
- 不把用户的一次修改自动升级为通用规则。
- 不使用、索取或暴露非授权的客户资料、项目名称或私有案例。

## 4. 使用模式

### 模式 A：快速初诊

**输入**：一段客户表达、聊天记录摘要或很短的 Brief。

**目标**：判断目前能否进入方案讨论；若不能，先补什么。

**输出**：

- 表面诉求与可能的项目目标；
- 已确认事实与来源；
- 基础资料齐备度；
- 客户需补充或确认的事项；
- 团队需要思考的方案命题；
- 仅针对真正阻断项的风险提示；
- 优先追问的 3—5 个问题。

### 模式 B：标准需求访谈

**输入**：客户已有资料，或用户愿意按轮回答问题。

**目标**：形成可与客户确认、可交给内部团队执行的需求底稿。

**行为**：每轮只追问会改变判断或下一步的事项；当关键信息已足够，停止追问并汇总。

**输出**：客户需求确认单、基础资料清单、内容提资清单、方案命题清单、项目启动 Brief、待确认事项与责任人建议。

### 模式 C：内部接单 / 启动评审

**输入**：已有客户资料、会议记录及不同角色的理解。

**目标**：识别团队理解差异、不可承诺项和项目风险。

**输出**：需求完整度、资料齐备度、内容与设计任务、关键矛盾、建议服务范围、必须确认事项、下一步行动清单。

## 5. 通用内核与行业判断包

每一条客户需求都可以先经过“轻量扫描”，但不是每个需求都必须跑完整诊断。

| 层级 | 内容 | 首版策略 |
| --- | --- | --- |
| 通用内核 | 目标、受众、场景、范围、资源、周期、决策链、交付、成功标准、风险 | 所有客户委托型项目可用 |
| 内容与设计转译层 | 内容命题、叙事结构、展示媒介、互动体验、视觉层级、运营更新 | 将需求变为方案方向，不当作风险清单 |
| 行业判断包 | 展陈资料、动线体验、现场限制、搭建周期、审批、制作与运营 | 首版优先服务展陈 / 活动 / 空间类项目 |
| 专业复核 | 法律、工程、消防、精确成本和合规承诺 | 只标记“需复核”，不替代专业人员判断 |

### 分流规则

- 输入短、目标不明：默认使用模式 A。
- 信息足以影响项目范围但尚未确认：进入模式 B。
- 输入来自多个内部角色或即将立项：进入模式 C。
- 用户只要求改写文案、翻译或做一个局部任务：不强制启动诊断，只在该任务受需求不清影响时提示可选初诊。

## 6. 十维需求地图

| 维度 | 要判断什么 | 缺失时的优先追问 |
| --- | --- | --- |
| 1. 项目目标 | 希望发生什么改变，而不只是要做什么形式 | “完成后，最希望谁产生什么变化？” |
| 2. 核心受众 | 谁会使用、观看、决策或受影响 | “最重要的对象是谁？他们现在的状态是什么？” |
| 3. 场景与时点 | 在哪里、何时、以何种环境发生 | “实际发生的场地、时间与限制是什么？” |
| 4. 内容与体验 | 要传达什么、希望如何被理解或体验 | “必须保留的内容与最想让人记住的是什么？” |
| 5. 范围与交付 | 本次委托具体包含和不包含什么 | “这次希望我们交付到哪个阶段？” |
| 6. 资源与预算 | 可投入的人、钱、既有资产与外部条件 | “目前可确认的资源边界是什么？” |
| 7. 时间与节点 | 真正不可移动的时间点和原因 | “哪个节点不可调整？若延后会有什么后果？” |
| 8. 决策链 | 谁提出、谁使用、谁拍板、谁协调 | “最终确认人是谁？还有谁会影响决定？” |
| 9. 成功标准 | 怎样才算有效、可接受或成功 | “项目结束后，依据什么判断它达到目的？” |
| 10. 风险与依赖 | 需要外部确认、可能变动或可能失败的条件 | “有哪些尚未定稿、需审批或依赖第三方的事项？” |

## 7. 来源归属与基础资料治理

### 7.1 每条结论必须标记来源

| 来源标签 | 可作为什么使用 | 不得被改写为 |
| --- | --- | --- |
| 客户原始 Brief | 客户目标、明确需求、已给条件 | 团队已承诺的方案 |
| 客户补充资料 | 可验证的内容资产、技术条件、品牌资料、场地资料 | 未经确认的客户立场 |
| 内部方案草案 | 团队当前的创意解读、策展方向、待讨论方案 | 客户原始需求或已确认事实 |
| AI 推断 | 需要验证的工作假设 | 客户事实或专业结论 |
| 待客户确认 | 尚未形成答案的决定、资料或授权 | 风险结论，除非它已阻断当前工作 |

当同一命题在不同材料中的归属不一致时，应显式提示“来源待核对”，不得自动选择较强的说法。

### 7.2 展陈项目的基础输入清单

在讨论创意前，Skill 必须先检查以下资料，并标记“已提供 / 待提供 / 不适用”以及它影响的工作阶段。

| 输入类别 | 最小输入 | 主要影响 |
| --- | --- | --- |
| 品牌与视觉资产 | 公司/品牌介绍、产品架构、VI、Logo 源文件、字体、可用图片与版权 | 品牌表达、视觉设计、内容校准 |
| 内容与证据资产 | 企业历程、产品介绍、技术数据、案例、影片、人物、客户/伙伴授权、数据出处 | 策展大纲、展项内容、可信度 |
| 场地与工程资料 | CAD/平面图、层高、机电消防、荷载、物业或场馆手册、现状照片 | 空间方案、报价、施工可行性 |
| 来访与接待资料 | VIP 分层、人数、参观时长、讲解路线、会议/签约/媒体需求、安保权限 | 动线、接待体验、功能布局 |
| 互动与运行资料 | API/本地部署、硬件与网络、并发量、设备清单、内容审核、运维与更新责任 | 互动设计、系统架构、运营方案 |
| 商务与治理资料 | 预算边界、采购范围、关键节点、决策人、验收标准、保密和审批规则 | 服务边界、排期、合同和风险判断 |

### 7.3 大纲前与大纲后的两轮提资

- **大纲前提资**：收集品牌、场地、核心内容、受众、业务目标与基础条件，用来判断“项目讲什么、给谁讲、在什么条件下讲”。
- **大纲后提资**：按每个展区或方案模块收集可上墙/上屏/入片/入互动的精确素材、数据、案例、版权、接口人与审核人，用来判断“这一段具体怎么讲、用什么媒介讲、谁确认”。

## 8. 内容与设计转译

Skill 不替代创意总监，但应将客户资料转为团队可讨论的方案命题。

| 转译维度 | 团队需要回答的问题 |
| --- | --- |
| 核心命题 | 客户真正希望观众相信、理解或行动的是什么？ |
| 叙事结构 | 信息应按什么因果或体验路径展开，而不是按部门资料堆放？ |
| 受众分层 | 不同来访者看什么、在哪停留、带走什么结论？ |
| 内容层级 | 哪些是主叙事、证据、案例、补充信息和可持续更新内容？ |
| 展示媒介 | 哪些内容适合实物、模型、数据、影片、沉浸、互动或讲解？ |
| 空间与动线 | 体验高潮、接待节点、私密区、运营区和回流关系如何安排？ |
| 长期运营 | 哪些内容会更新，更新方式、审核人和维护机制是什么？ |

“主题待定”“展项怎样分级”“入口如何处理”“互动采用何种机制”默认属于方案命题；只有它已影响预算、工期、审批、合同或安全时，才同时进入风险判断。

## 9. 判断逻辑

### 9.1 四种证据标签

每一项结论必须使用下列其中之一标记，避免把推断写成事实：

| 标签 | 含义 | 表达方式 |
| --- | --- | --- |
| 已确认 | 用户或材料明确说明 | “已确认：……” |
| 待验证 | 合理推断但没有证据 | “当前推测：……，需确认。” |
| 风险 | 现有信息下可能造成返工、失控或误解 | “若……不变，可能导致……” |
| 选项 | 面对不确定性可选的取舍 | “可选 A / B；分别意味着……” |

### 9.2 六类冲突检查

1. **目标—形式冲突**：目标是转化、教育或传播，讨论却只停留在风格或设备。
2. **受众—内容冲突**：目标对象的知识、动机或行动路径未被内容回应。
3. **内容—场景冲突**：内容体量和体验方式不符合实际空间、时间或媒介条件。
4. **目标—资源冲突**：期待的效果与预算、周期、人力或既有资产不匹配。
5. **承诺—范围冲突**：客户期待的结果超过当前委托或责任边界。
6. **需求—决策冲突**：提出需求的人无权确认，或关键利益相关方尚未参与。

### 9.3 风险分级

- **红色**：若不先确认，将直接影响是否接单、报价、承诺、工期或合规；必须在下一步前处理。
- **黄色**：会显著影响质量、范围或协作方式；应在方案启动前处理。
- **绿色**：有优化空间但不阻断当前推进；记录即可。

不依据“客户表达是否专业”评分，只依据该缺口或冲突对项目决策的影响。

## 10. 固定输出协议

无论使用哪个模式，输出均按以下顺序呈现；模式 A 可简化，模式 B/C 可展开。

1. **项目命题与需求摘要**：客户表达与当前项目判断。
2. **来源明确的已知信息**：按“客户原始 Brief / 客户补充资料 / 内部方案草案”分别归档。
3. **基础资料齐备度**：按品牌、内容、场地、接待、运行、商务六类列出已提供和待提供项。
4. **客户补资与确认卡**：需要客户提供、授权、指定或确认的事项，以及它影响的阶段。
5. **内容与设计转译卡**：团队应形成的叙事、空间、媒介、体验、动线和运营命题。
6. **真正的风险与边界**：仅列出会影响报价、排期、落地、合规或合同的事项。
7. **下一步问题与行动**：按优先级排列，说明每一问或动作会改变什么决定。
8. **交接卡**：供大纲、方案、报价或项目管理继续使用的最小信息集。

## 11. 人工协作与反馈

用户可随时通过以下四类指令修正本 Skill：

- “这个判断太严 / 太松。”
- “这类项目必须先问 / 不要先问这个。”
- “这只是内部创意解读，不能写成客户需求。”
- “这是大纲前的基础提资，不是大纲后的分区素材。”
- “这只是某一客户的特殊偏好，不要推广。”
- “把它作为某类项目的默认规则。”

收到反馈后，Skill 的处理原则是：

1. 先记录为单个案例反馈；
2. 判断它是一次性偏好、行业条件还是候选通用规则；
3. 只有经人工批准、写入版本说明并通过回归测试的规则，才进入下一版本；
4. 未批准的反馈只影响当次对话，不改变产品默认行为。

## 12. 首版验收条件

SKL-001 进入封装前，必须在 6 个原子测试中做到：

- 缺资料时先追问，不自行补事实；
- 每项关键结论能分清客户原始需求、内部解读和待验证推断；
- 能同时输出客户补资、内容策展任务、设计命题和真正风险，而不混为一张缺口清单；
- 矛盾需求能明确指出冲突及影响；
- 对普通且清晰的需求不过度盘问；
- 输出能明确给出下一步而非停在分析；
- 不出现客户、项目、案例、私有资料或来源暗示；
- 人工能够定位、采纳、修改或删除每一项关键判断。

## 13. 仍待你校准的决策

1. 首版是只面向线下策划类项目，还是允许以“通用客户项目诊断”对外描述？
2. 快速初诊中，预算是否应成为默认必问项，还是只在已进入方案/报价阶段再问？
3. 红色风险是否需要给出“暂不承诺”的明确措辞？
4. 首版输出更偏客户可见的确认单，还是更偏内部团队的接单判断卡？
5. 哪些判断必须保留为你的人为裁决，而不应由 Skill 先给建议？
6. 展陈类首版的基础资料清单中，哪些项目必须在大纲前拿到，哪些可在大纲后按展区补齐？
